# ADR-003 — مصدر الحقيقة لمخطط قاعدة البيانات

**الحالة:** Architectural Decision Required

## ما اكتشفناه

- مستودع `clinic-evaluator` لا يحتوي حالياً على مجلد `supabase/migrations` أو ملفات schema/migration ضمن شجرة المشروع.
- مشروع Supabase الحالي يُرجع **0 migrations** مسجلة.
- رغم ذلك توجد حالياً جداول، سياسات RLS، دوال PostgreSQL، Edge Functions وبيانات تشغيلية فعلية على المشروع الحي.

هذا يعني أن جزءاً مهماً من بنية الإنتاج موجود خارج Git وغير ممثل كمسار تغييرات قابل لإعادة البناء من المستودع.

## لماذا هذا مهم

لدينا الآن قرار معماري واضح يفصل الإدارة عن المستخدم العام ويجعل نتيجة التقييم رسمية من الخادم.

لتنفيذ هذا بأمان نحتاج معرفة أن:

> ما في الإنتاج يمكن إعادة بنائه واختباره من نسخة محفوظة في المستودع.

بدون ذلك تصبح تغييرات قاعدة البيانات معتمدة على ما تم فعله يدوياً في لوحة Supabase في الماضي، ويصبح من الصعب:
- إعادة إنشاء المشروع.
- إنشاء بيئة اختبار مطابقة.
- معرفة متى ولماذا تغيرت الصلاحيات.
- مراجعة RLS والدوال ضمن Git.
- تنفيذ rollback منظم.
- ضمان أن staging وproduction متطابقان.

## الخيارات

### Option A — الاستمرار بإدارة قاعدة البيانات يدوياً

تستمر قاعدة البيانات الحية كمصدر الحقيقة، ويُستخدم Git للكود فقط.

المقابل: لا توجد طريقة قوية ومضمونة لإعادة بناء الحالة الحالية من المستودع.

### Option B — جعل Git مصدر الحقيقة للمخطط

يتم استخراج المخطط الحالي بعد تدقيقه وتنظيفه، ثم وضع schema/migrations في Git، وتصبح التغييرات المستقبلية عبر migrations versioned.

المقابل: يحتاج الأمر إلى إنشاء baseline دقيقة للمخطط الحالي قبل اعتمادها.

### Option C — Git + بيئة اختبار مستقلة

نجعل Git مصدر الحقيقة، ونضيف بيئة staging/preview تُختبر عليها migrations قبل الإنتاج.

هذا يوفر أعلى مستوى من الانضباط، لكنه يتطلب بيئة إضافية ومسار نشر أكثر تنظيماً.

## المقترح

بالنسبة لحجم Clinic Evaluator الحالي، الاتجاه الموصى به هو:

**Option B الآن، مع تجهيز البنية بحيث يمكن إضافة Option C لاحقاً.**

أي:
1. استخراج schema الإنتاج الحالي.
2. مراجعته وعدم تحويل الأخطاء الحالية إلى baseline غير مرغوب.
3. تسجيله في Git.
4. اعتبار كل تغيير لاحق migration موثقاً.
5. عدم تنفيذ أي migration على الإنتاج قبل التحقق منها على نسخة اختبارية عند توفرها.

Supabase توصي بتخزين migrations في `supabase/migrations` للحفاظ على اتساق المخطط بين البيئات، وتدعم سحب مخطط مشروع قائم قبل بدء هذا المسار.
