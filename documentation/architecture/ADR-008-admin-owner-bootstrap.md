# ADR-008 — تعيين هوية مالك النظام

**الحالة:** Accepted / Implemented

## السبب

ADR-004 يعتمد Supabase Auth للهوية و`admin_users` كمصدر الحقيقة للصلاحيات، مع مالك أساسي واحد لا يمكن إنشاء مالك ثانٍ أو نقل الملكية عبر واجهة الإدارة.

تم تنفيذ طبقة `admin_users` مع RLS وقيود singleton للمالك، تم الآن اختيار حساب المالك صراحةً من مالك المشروع، ولم يعد اختيار المالك افتراضياً أو آلياً.

## القرار المعتمد

حساب Supabase Auth `yazeed48@gmail.com` يمثل **مالك النظام الأساسي للتطبيق**، وتمت تهيئة سجل واحد له في `admin_users` بدور `owner` وحالة `active=true`.

لا يجوز للهندسة اختيار الحساب تلقائيًا أو اعتبار أول مستخدم هو المالك، لأن ذلك يحول قرار ملكية النظام إلى افتراض أمني.

## ما تم تنفيذه

- جدول `admin_users` مرتبط بـ`auth.users`.
- الدوران المسموحان: `owner` و`admin`.
- قيد فريد يمنع أكثر من مالك واحد.
- RLS مفعّل.
- إنشاء المديرين الجدد مسموح للمالك فقط.
- تحديث/حذف سجلات المديرين delegated admins مقيّد بالمالك.
- لا توجد سجلات إدارية حاليًا.

## ما تم تنفيذه بعد القرار

- تسجيل دخول لوحة الإدارة أصبح عبر Supabase Auth بالبريد الإلكتروني وكلمة المرور.
- بعد تسجيل الدخول يتم التحقق من `admin_users` باستخدام JWT؛ لا يكفي وجود حساب في `auth.users` وحده.
- يتم تمرير JWT المستخدم إلى عميل REST الخاص بلوحة الإدارة بدلاً من جلسة `localStorage` أو كلمة مرور ثابتة.
- تم إغلاق استدعاءات الإدارة القديمة المجهولة، وإضافة حارس `require_admin()` لدوال الإدارة الحساسة.
- تم تثبيت `search_path` لدوال `SECURITY DEFINER` الإدارية.

**الحد المتبقي:** الاختبار التشغيلي الفعلي لتسجيل الدخول يحتاج تنفيذ المستخدم من المتصفح بكلمة مرور الحساب؛ لا يتم تخزين كلمة المرور في المستودع أو السجلات.
