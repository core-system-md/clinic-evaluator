# ADR-004 — هوية الإدارة وصلاحيات Owner/Admin

**الحالة:** Architectural Decision Required

## ما نعرفه الآن

- قرار ADR-001 اعتمد وجود Owner واحد وإداريين بحسابات إدارية حقيقية.
- مشروع Supabase يحتوي حالياً على 5 مستخدمين في Auth.
- لا يوجد حالياً أي claim إداري في raw_app_meta_data للمستخدمين الحاليين.
- الكود الحالي لا يحتوي مسار signInWithPassword أو نظام صلاحيات إداري حقيقي.
- بوابة الإدارة الحالية تعتمد على كلمة مرور ثابتة محلياً في المتصفح وlocalStorage، بينما مدير الإدارة يستخدم العميل العام نفسه.
- Supabase Auth مصمم للمصادقة، ويمكن دمجه مع RLS لتطبيق التفويض. توصي أدلة Supabase بوجود جدول أدوار/صلاحيات، وبإمكان Auth Hook إضافة الدور إلى JWT عند الحاجة. كما يجب عدم استخدام user_metadata لاتخاذ قرارات التفويض لأنها قابلة لتعديل المستخدم؛ ويمكن استخدام app_metadata للـclaims، مع الانتباه إلى أن JWT قد لا يتحدث فوراً بعد تغيير الدور.

## القرار المطلوب

### Option A — app_metadata / JWT فقط

يكون الدور مثل owner أو admin داخل app_metadata ويستخدم في JWT/RLS.

**الميزة:** بسيط.

**المقابل:** تغيير الدور لا يصبح موجوداً في الـJWT القديم حتى يحصل المستخدم على token جديد/refresh.

### Option B — جدول إداري مستقل

إنشاء جدول مثل admin_users مرتبط بـauth.users ويحتوي user_id وrole (owner/admin) وactive وcreated_at وupdated_at.

ويكون هذا الجدول هو المصدر الرسمي للحقيقة للصلاحيات.

يمكن استخدام دالة تحقق صغيرة وآمنة في RLS، أو فحص الخادم مباشرة، مع إبقاء الجدول غير قابل للقراءة/التعديل من المستخدمين العاديين.

**الميزة:** يمكن إلغاء صلاحية إداري مباشرة من مصدر واحد، مع سجل واضح لمن هو Owner ومن هو Admin.

**المقابل:** يحتاج طبقة صغيرة إضافية للصلاحيات.

### Option C — نظام Roles + Permissions كامل من البداية

بالإضافة إلى Owner/Admin، نبني جدولاً للصلاحيات التفصيلية من البداية.

**الميزة:** مرونة أعلى.

**المقابل:** تعقيد غير ضروري ما دام عدد الأدوار المطلوب حالياً محدوداً.

## الاتجاه المقترح

**Option B الآن**، مع تصميمه ليقبل صلاحيات تفصيلية لاحقاً.

الدوران الأوليان:

- owner: حساب واحد فقط، مالك النظام، يستطيع إدارة الإداريين وجميع وظائف النظام.
- admin: إداري يمكن منحه الصلاحيات التشغيلية المطلوبة، لكن لا يستطيع إنشاء Owner آخر أو تغيير ملكية النظام.

يمكن لاحقاً تحويل الصلاحيات التشغيلية إلى مجموعة permissions بدون تغيير هوية المستخدمين أو مصدر الحقيقة.

## قواعد أمنية

- Supabase Auth هو مصدر هوية المستخدم.
- جدول admin_users هو مصدر الحقيقة للتفويض الإداري.
- لا تعتمد الصلاحيات على localStorage أو على وجود عنصر مخفي/ظاهر في واجهة الإدارة.
- لا تُستخدم user_metadata لاتخاذ قرارات التفويض.
- أي دالة SECURITY DEFINER لازمة للتحقق يجب أن تكون محدودة ومحصنة، وليست بوابة CRUD عامة.
- لا يتم إرسال أي secret/service key إلى المتصفح.

**لا يتم تنفيذ التغيير الإنتاجي قبل اعتماد هذا القرار.**
